# Document processing and conversation data model

Verified on 2026-10-08 with PostgreSQL, pgvector, EF Core 10, and the existing Identity schema. This step provides persisted models and job state transitions. Upload endpoints, storage, extraction, embedding API calls, retrieval services, chat endpoints, and the worker polling/recovery loop remain future work.

## Entities and relationships

- Document belongs to an ApplicationUser. It stores a display filename (maximum 255 characters), an opaque unique storage key (16–128 letters/digits/underscore/hyphen), UTC upload time, Pending/Processing/Ready/Failed status, and an optional allowlisted failure code. FailureMessage is derived safe text and is not persisted. Filenames are untrusted labels; storage keys are generated by the application and never accepted as filesystem paths.
- DocumentChunk belongs to a document. Its zero-based Position is unique within that document. Text is required and bounded to 32,000 characters. PageStart/PageEnd are either both absent or a valid inclusive one-based range. Embedding may be null while processing; its model identity is always required.
- ProcessingJob belongs to a document. Attempts, retry availability, lease identity/expiry, start/completion timestamps, safe last failure, and PostgreSQL xmin persist the retry/recovery state. One queued/running job is allowed per document; terminal history permits a later new job.
- Conversation belongs to an ApplicationUser and optionally one Document. A null DocumentId means a future conversation across the user's corpus. The composite document foreign key includes OwnerId, so a document-scoped conversation cannot refer to another user's document.
- Message belongs to a conversation. Its zero-based Position is unique within that conversation, and its required text is bounded to 64,000 characters. User/Assistant/System roles are constrained in the database; future HTTP request contracts must allow clients to submit only user turns.

Document deletion cascades to chunks/jobs; conversation deletion cascades to messages. A document referenced by a conversation has restricted deletion so the future delete service must make an explicit history-retention decision. Identity-owner foreign keys cascade owned rows, but account deletion also needs an explicit transaction that removes conversations before referenced documents. Private file deletion is separate from database cascades and needs durable cleanup in a future storage service.

Configurations live in Data/Configurations, discovered by DocuMindDbContext. They enforce required foreign keys, unique ordering/storage keys, valid enums, nonempty/bounded text, page ranges, safe failure state, and retry/lease invariants. Owner/time indexes support chronological lists; partial queued/expired-lease indexes support future worker polling. Constraints defend persisted invariants; request validation must still give helpful HTTP errors.

## Embedding contract

The initial selected model is **openai/text-embedding-3-small with 1,536 dimensions**, using the model's default output size. EmbeddingContract is the shared constant, and the database enforces both vector(1536) and the exact model identity. Nonzero vectors are required for cosine distance; null vectors represent incomplete work and are excluded from the HNSW cosine index.

This table is one compatible search space. It rejects a different model even if that model also produces 1,536 dimensions. There is no embedding provider configured or contacted by this step, and no API key was added. The future embedding service must request this exact model/output size for both document and question vectors and validate returned dimensions. Changing model, dimensions, or preprocessing compatibility requires a deliberately versioned contract, schema/index migration, and re-embedding or a separate table/search space; do not relabel old vectors or combine them in one similarity query. Provider/model revisions need the same compatibility decision.

Pgvector.EntityFrameworkCore 0.3.0 supports EF Core 9 and 10 according to its maintained documentation. Existing EF/Identity 10.0.12 and Npgsql EF provider 10.0.3 versions were retained. UseDocuMindPostgreSql centralizes the required UseVector mapping for runtime, migration tooling, and integration checks.

Official references: [pgvector .NET adapter and EF support](https://github.com/pgvector/pgvector-dotnet), [embedding dimensions](https://developers.openai.com/api/docs/guides/embeddings), [pgvector indexing](https://github.com/pgvector/pgvector), and [Npgsql xmin concurrency](https://www.npgsql.org/efcore/modeling/concurrency.html).

## Ownership in subsequent services

Future document/conversation endpoints must require authentication. Controllers obtain the Guid user ID from the authenticated Identity principal and pass it to Services. Creation assigns OwnerId on the server; never bind it from a browser request. Lookups, updates, downloads, deletion, message access, chunk access, and vector ranking must include ownership in SQL. Return the same 404 for missing and unowned IDs.

There is deliberately no request-dependent global query filter or PostgreSQL row-level security in this step: the worker must process jobs across owners, while request services must explicitly scope every query. A valid foreign key proves the owner exists; it does not authorize the caller. The database composite foreign key prevents cross-owner conversation/document associations, and an integration check proves an owner-scoped cosine query excludes another user's equally similar chunk. HTTP ownership enforcement is still to be implemented with the corresponding services.

Examples for future Services code (the database, authenticatedOwnerId, requested IDs, cancellationToken, and queryVector come from validated server-side inputs):

~~~csharp
// Filter before selecting a safe response: do not expose StorageKey, failure internals, or navigation graphs.
var document = await database.Documents.AsNoTracking()
    .Where(item => item.Id == documentId && item.OwnerId == authenticatedOwnerId)
    .Select(item => new { item.Id, item.DisplayFileName, item.UploadedAt, item.Status, item.FailureCode })
    .SingleOrDefaultAsync(cancellationToken);

// Access a message only through a conversation that belongs to the authenticated principal.
var messages = await database.Messages.AsNoTracking()
    .Where(item => item.ConversationId == conversationId && item.Conversation.OwnerId == authenticatedOwnerId)
    .OrderBy(item => item.Position)
    .Select(item => new { item.Id, item.Role, item.Content, item.CreatedAt })
    .ToListAsync(cancellationToken);

// Scope documents and compatible completed vectors in SQL before ranking and limiting.
// Add a requested-document predicate as well when the conversation is document-scoped.
// CosineDistance requires using Pgvector.EntityFrameworkCore; queryVector uses EmbeddingContract.
var chunks = await database.DocumentChunks.AsNoTracking()
    .Where(item => item.Document.OwnerId == authenticatedOwnerId
        && item.Document.Status == DocumentProcessingStatus.Ready
        && item.EmbeddingModel == EmbeddingContract.Model && item.Embedding != null)
    .OrderBy(item => item.Embedding!.CosineDistance(queryVector))
    .Take(5)
    .Select(item => new { item.DocumentId, item.Position, item.Text, item.PageStart, item.PageEnd })
    .ToListAsync(cancellationToken);
~~~

Approximate vector indexing plus selective owner filters can return fewer candidates than requested. The retrieval implementation must evaluate recall and appropriate iterative scanning or exact scoped search; the current checker verifies exclusion and SQL translation, not production retrieval quality.

## Worker retry and recovery protocol

ProcessingJob's methods make decisions; callers must save them. The worker loop is not implemented by these methods.

1. Load a due queued job with tracking, create a fresh random lease Guid, call TryClaim, then SaveChanges before contacting storage/providers. xmin concurrency means competing snapshots cannot both save their claim. Catch DbUpdateConcurrencyException and abandon/reload the losing claim.
2. Heartbeat through TryRenewLease and persist it before expiry. The worker must use UTC, conservative lease durations, and a fresh clock; an expired lease cannot be revived.
3. On success, check the current lease through TryComplete and write chunks, the Ready document state, and job completion in one database transaction. A failed xmin check must roll back all publication. External file writes require separate staging/idempotency; never publish them merely because an in-memory method returned true.
4. On failure, call TryFail with a safe ProcessingFailureCode and bounded retry delay. Requeue until MaxAttempts (default five, database bounds one through ten) is reached; then record Failed/completion time and update the document's Failed/FailureCode state in the same transaction. Keep exception details only in private logs.
5. A recovery sweep loads expired running jobs and calls RecoverExpiredLease, then saves with concurrency checks. A crash consumes its claimed attempt. Recovery requeues within the budget or terminates an exhausted job; a later claim gets a different lease ID. Stale workers cannot save over that newer xmin.
6. The future worker must check database/current lease ownership at publication time, promptly commit before expiry, and retry transactions safely. The model does not schedule polling, synchronize clocks, perform heartbeats, or impose a database wall-clock deadline automatically. Unique chunk ordering and transactional replacement/upserts will make processing retries idempotent.

The PostgreSQL checker exercises concurrent claim conflicts, expired-lease recovery, replacement leases, stale completion rejection, retry delays, final-attempt crashes, and persisted terminal state.
